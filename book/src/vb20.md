# Correspondence with the vb20 pairing accumulator

> **In short.** This crate keeps the type and method names of the
> [vb20 pairing accumulator](glossary.md#vb20-pairing-accumulator), an earlier accumulator built
> on pairings, which are not post-quantum. This chapter says where the two differ and maps every
> item of one to the other.
>
> **Read this when** you port code written for the vb20 pairing accumulator, or know that API
> and want to find its counterpart here.
>
> **New here?** You can skip this chapter unless you come from the vb20 pairing accumulator. If
> you do, read [A porting hazard](#a-porting-hazard) first.

The crate's API mirrors the vb20 pairing accumulator: the same type names and the same method
names, so that code written against one reads the same against the other. This chapter says
where the two differ and maps every item.

## What is the same

The crate has counterparts, with the same method names, for the vb20 pairing accumulator's
`Element`, `Coefficient`, `Accumulator`, `SecretKey`, `PublicKey`, `MembershipWitness`,
`Delta`, `evaluate_delta`, `evaluate_deltas`, `ProofParams`, `MembershipProofCommitting`,
`MembershipProof` and `MembershipProofFinal`.

## What differs, and why

The differences follow from the lattice scheme.

- **State.** The paper's algorithms keep state between calls and the vb20 pairing accumulator
  does not. Methods whose paper algorithm keeps state take a `ManagerState` as their last
  argument. See [Manager state and its tag](state.md).
- **Public key arguments.** Witness updates depend on the public matrices, so methods that
  need them take a `PublicKey` last.
- **Randomness.** Randomness comes from a generator argument rather than from the operating
  system's generator.
- **Errors.** Every fallible operation returns `Result` where the vb20 pairing accumulator
  returned a value, unwrapped, or skipped silently. See [Errors](errors.md).
- **Elements.** An element is an `ℓ`-bit string, not a field element. The outer proof
  challenge is a 64-byte `Challenge` for the same reason.
- **Additions are free.** Adding does not change the value and publishes nothing, so the batch
  polynomial machinery of the pairing scheme has no counterpart.
- **[Positive](glossary.md#positive) only.** Non-membership witnesses and proofs are absent.
- **Linking.** A membership proof links to an outer credential through a relation
  `A₁·x + A₂·r = t` rather than a shared Schnorr blinder. See
  [Membership proofs](proofs.md).
- **By reference.** Values that the types of the vb20 pairing accumulator take by copy are
  taken by reference here.
- **No `Display`.** Values are too large to print; `Debug` and the hex serde forms serve
  instead.

## A porting hazard

Equal names do not mean equal obligations. Three things that are harmless with the pairing
accumulator matter here.

- **The manager state must be kept, persisted and never rolled back.** The pairing accumulator
  has no such thing. A [rollback](glossary.md#rollback) or a fork cannot leak the key, but it publishes a second
  history that holders of the first cannot follow.
- **An element can be added only once** in Construction 4.1. Code that removes and re-adds the
  same element must move to the [adaptive variant](adaptive.md).
- **Deletions are bounded.** At most [`γ`](glossary.md#deletion-bound) over the life of the accumulator.

[Misuse](misuse.md) has the full list.
